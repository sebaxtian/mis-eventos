# Tareas de verificación y cierre: Entrega y Release v1.0.0 (`delivery`)

| Campo                  | Valor                         |
| ---------------------- | ----------------------------- |
| **ID del dominio**     | `DLV`                         |
| **Spec de referencia** | `specs/delivery/spec.md` v1.1 |
| **Plan de referencia** | `specs/delivery/plan.md`      |

> Ninguna tarea empieza hasta que la spec esté _Aprobada_ (R1.8). Cada tarea sigue el ciclo test → rojo → implementación mínima → verde → refactor (R3.1). El rojo debe fallar por la aserción esperada (R3.2).

**Estados:** `[ ]` pendiente · `[R]` test en rojo · `[V]` verde · `[x]` refactorizada y cerrada

> **Por qué no hay secciones `## Backend` ni `## Frontend`.** `delivery` no produce código de producto: no crea endpoints, routers, modelos, migraciones, schemas, componentes, stores, servicios ni dependencias (`DLV-BR-01`). Por eso las secciones de la plantilla se sustituyen por bloques de **verificación y cierre**. El parche de metainformación (`pyproject.toml`, `uv.lock`, `package.json`, `package-lock.json` y el parámetro `version` de `FastAPI`) se ejecuta dentro de `## Versiones y release` y no constituye funcionalidad ni cambio de contrato.
>
> **Cómo se satisface R1.5** (decisión `DLV-D2`, opción A, 2026-11-01): cada criterio `DLV-AC-NN` se cubre con un comando reproducible y una evidencia verificable, reutilizando el test existente cuando el comportamiento pertenece a otro dominio (por ejemplo `test_plat_ac_12_docker_compose_and_nginx_gateway_routing` para `DLV-AC-15`/`DLV-AC-17`). No se escriben tests de aserción sobre documentación ni se tocan las suites de producto.
>
> **Endurecimiento de infraestructura descartado** (`DLV-D4`, fuera de alcance): no hay tareas para retirar los puertos `5432`/`6379`, añadir cabeceras de seguridad en Nginx ni políticas `restart:` en Compose; la limitación se declara en `CHANGELOG.md`.
